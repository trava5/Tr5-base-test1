# Title

Add project/checklist.md HTML page implementation checklist

---

# Purpose

The owner wants a concrete, written-down plan for a future small task (building a simple HTML page with a blue background and black "HELLO WORLD!" text) before any code for it is written. Capturing this as a checklist document first lets the actual HTML/CSS implementation be scoped and reviewed as its own later contract, instead of code being written ad hoc without a prior plan.

---

# Intent

This contract deliberately produces only a planning artifact: a markdown bullet-list checklist of the steps needed to build the described HTML page. It deliberately does not create, modify, or reference any actual .html/.css file, and does not execute or validate any of the listed steps — that is left to a future contract. It relates to the existing architecture only through project/, which already holds project/README.md and project/hello.md and is documented as the location for every implementation contract's actual output (project/README.md, 'Purpose').

---

# Current State

Per memory/CURRENT_STATE.md (regenerated by the Discovery Engine before this contract), project/ currently contains exactly two files: README.md and hello.md. No checklist.md, and no HTML/CSS file of any kind, exists anywhere in the repository. project/README.md documents project/ as the location where every contract's actual code/content changes land.

---

# Inputs

None beyond the request itself — no existing module, API, or data file is read or built upon.

---

# Outputs

A new file project/checklist.md containing a markdown bullet-list checklist of the steps needed to create a simple HTML page with a blue background (background-color: blue) and black "HELLO WORLD!" text. No other file is created or modified.

---

# Functional Requirements

## Point 1

SHALL: Create the file project/checklist.md containing a markdown bullet-list (using `-` list items, no numbered list, no headings other than an optional single top-level title, no code blocks) that lays out, in order, the concrete steps needed to create a simple HTML page with a blue background and black "HELLO WORLD!" text — for example: creating the HTML file, adding the basic HTML document structure, setting the body background color to blue, adding an element containing the text "HELLO WORLD!", setting that text's color to black, and opening/checking the result in a browser.

Acceptance criteria:
- File project/checklist.md exists after implementation, using exactly this lowercase_with_underscores filename.
- No file named project/CHECKLIST.md or any other case variant exists in the repository.
- The file's content is a markdown bullet list (list items starting with `-`); it contains no actual HTML, CSS, or JS code (no `<`...`>` tags, no CSS rule blocks with `{`/`}`, no fenced code blocks).
- The checklist explicitly includes a step mentioning a blue background (e.g. referencing 'blue' and 'background') and a step mentioning black-colored text reading exactly "HELLO WORLD!".
- The checklist contains at least 4 distinct steps, each as its own bullet item.
- No file other than project/checklist.md is created, modified, or deleted.

1) Purpose/Intent: matches a real, explicitly stated owner request (a written plan before code is written for a future small HTML task) — not the architect inventing scope. The contract's own Intent section correctly scopes itself to only the planning artifact and defers the actual HTML/CSS to a future contract, consistent with P1 ('implementation reflects today's understanding, not tomorrow's assumption') and the Future Evolution section's explicit deferral note.

2) Contract-vs-light-path: creating project/checklist.md is a new file, which AGENTS.md's light-path section explicitly excludes ('must not introduce ... a new ... file ... As soon as it does, it needs a contract'), so routing this through the full contract pipeline rather than a light-path fix is correct, not overkill.

3) Current State accuracy verified directly (not taken on faith): Glob confirmed project/ contains exactly README.md and hello.md; memory/CURRENT_STATE.md (Discovery Engine output) confirms the same two files and no checklist.md/HTML/CSS anywhere in the repo, and project/README.md documents project/ as the landing zone for contract output — all matching the contract's 'Current State' text verbatim (P6/P7 compliance).

4) Points: single point, actionable, with a concrete, mechanically checkable acceptance-criteria list (exact filename, no case variants, bullet-list-only format with explicit exclusions for HTML/CSS/code-block syntax, required content markers for 'blue'/'background' and the exact text 'HELLO WORLD!', a minimum step count, and a no-other-file-touched constraint). No ambiguity that would force the programmer to guess.

5) Out of Scope: explicitly bars creating/modifying any .html/.css/.js file, modifying README.md/hello.md or anything outside project/, adding executable code/tooling, and creating a case-variant filename — covers the realistic edge cases for a task this size.

6) Backward compatibility: N/A — new file only, no existing behavior/API touched.

7) Permissions/destructive commands: none required beyond a single file create inside project/, well within the programmer's `edit` permission profile and within AGENTS.md's project/-by-default write scope (ADR-022); no governance `.md` or framework `.py` file is touched.

8) Naming convention (ADR-008): project/checklist.md is lowercase_with_underscores, ASCII, no hyphens — correctly classified as a free-form content file (not a rule/role/state/contract-bearing document), consistent with the existing precedent of project/hello.md (also lowercase) sitting alongside project/README.md.

9) Risk level: contract declares 'standard'. Checked against the decision-7 criteria recorded in ADR-030 (real credentials/API keys, real external-system calls, native/hardware libraries, risk of landing personal/real data in git) — none apply; this is a pure local markdown-file write with no external interaction. No escalation warranted.
